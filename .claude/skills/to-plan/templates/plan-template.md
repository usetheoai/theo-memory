# Plan Template

Every plan generated by `/to-plan` MUST follow this structure. Each section is mandatory unless marked (optional).

This file is the canonical template referenced from `to-plan/SKILL.md § Plan Template`. To produce a new plan, copy everything inside the `<plan-template>` block below into `.claude/knowledge-base/plans/{slug}-plan.md` and replace placeholders.

<plan-template>

# Plan: {Title}

> **Version 1.0** — one-paragraph executive summary explaining what this plan does, why it matters, and what the expected outcome is.

## Context

What exists today, what's broken or missing, and what evidence (data, logs, user reports, benchmark results) motivates this work. Include links to issues, PRs, or ADRs when available.

## Objective

One clear sentence: what does "done" look like? Then a short list of specific, measurable goals.

## ADRs

Architecture Decision Records for this plan. Each decision gets:
- **ID** (D1, D2, ...) for cross-referencing in tasks
- **Decision** — what was decided
- **Rationale** — why this approach over alternatives
- **Consequences** — what this enables and what it constrains

## Dependency Graph

ASCII diagram showing phase dependencies. Example:

```
Phase 0 ──▶ Phase 1 ──▶ Phase 2 ──▶ Phase 3
                │                       │
                │                       ▼
                │               Phase 3.1
                │
                ▼
          Phase 4 (parallel)
```

Annotate which phases can run in parallel vs which are sequential blockers.

## Phase N: {Title}

**Objective:** one sentence describing what this phase achieves.

### T{N}.{M} — {Task Title}

#### Objective
What this specific task accomplishes.

#### Evidence
Data, logs, or observations that justify this task. Why it's needed NOW, not later.

#### Files to edit
```
src/path/to/file.ts — what changes and why
src/path/to/other.ts — what changes and why
src/path/to/file.test.ts — RED test added first (TDD)
```

#### Deep file dependency analysis
For each file listed above, explain:
- What the file does today
- How this task changes it
- What downstream files depend on this change

#### Deep Dives
Technical details for non-obvious aspects:
- Data structures: exact fields, types, derive macros
- Algorithms: step-by-step logic
- Invariants: what MUST be true before and after
- Edge cases: empty inputs, zero values, missing fields, backward compat

#### Tasks
Numbered checklist of atomic implementation steps:
1. Step one
2. Step two
3. ...

#### TDD
Strict RED-GREEN-REFACTOR cycle. List every test FIRST:

```
RED:     test_name() — what it asserts (this test MUST fail before implementation)
RED:     test_name_2() — what it asserts
GREEN:   Implement the minimal code to make all RED tests pass
REFACTOR: What cleanup is expected (or "None expected")
VERIFY:  npm test -- {path}   (pytest for Python tools under .claude/skills/)
```

#### Acceptance Criteria
Bulleted list of observable, verifiable conditions:
- [ ] Criterion 1
- [ ] Criterion 2
- [ ] Pass: complexity — every changed file has cyclomatic complexity ≤ 10 (eslint-plugin-complexity or manual audit)
- [ ] Pass: coverage — `npm run test:coverage` ≥ 90% on changed files (critical paths: 100%)
- [ ] Pass: lint — `npm run lint` zero warnings on changed files
- [ ] Pass: size — every changed file ≤ 500 lines (see `.claude/rules/architecture.md § Module hygiene`)

#### DoD (Definition of Done)
- [ ] All tasks completed and validated
- [ ] All tests passing — `npm test` green
- [ ] Zero TypeScript errors — `npm run typecheck`
- [ ] Zero lint warnings — `npm run lint`
- [ ] File-size budget respected (per `architecture.md`)

## Global Definition of Done

- [ ] All phases completed
- [ ] All tests passing — `npm test` green (TypeScript) + `pytest .claude/skills/plan-confidence/tests` (Python tools, when touched)
- [ ] Zero TypeScript errors — `npm run typecheck`
- [ ] Zero lint warnings — `npm run lint`
- [ ] File-size budget respected (per `.claude/rules/architecture.md § Module hygiene`)
- [ ] CHANGELOG.md updated under `[Unreleased]` (Inquebrável Rule 6) once the file exists in the repo
- [ ] Backward compatibility preserved across public API (`src/index.ts` and subpath exports)
- [ ] Plan-specific criteria (list them explicitly)
- [ ] **Runtime-metric proof** — for every task whose DoD references a runtime counter (cache-hit rate, dedup-collision rate, embedding-batch fill rate, BM25 vs semantic share, etc.), the metric MUST be observed non-zero in an integration workload (`npm test -- tests/integration/`), not just verified to compile. "Code exists + tests pass" is NOT proof the wiring fires in real workloads.

## Final Phase: Integration Validation (MANDATORY)

> This phase runs AFTER all implementation phases are complete. The plan is NOT done until the integration validation chain passes.

**Objective:** Validate that the implemented changes work in a real workload — not just as isolated unit tests.

### Execution

Run the full validation chain:

```
npm test                        # unit + integration tests
npm run test:coverage           # coverage report (≥ 90% on changed files)
npm run typecheck               # zero TS errors
npm run lint                    # zero lint warnings
```

If the project has e2e tests (TheoKit binding paths):

```
npm run test:e2e
```

### Acceptance Criteria

- [ ] All test suites green (unit + integration + e2e when present)
- [ ] Coverage ≥ 90% on changed files (critical paths: 100% — extraction pipeline, retrieval scorer, dedup)
- [ ] Zero TypeScript errors
- [ ] Zero lint warnings
- [ ] Runtime-metric proof — for any task referencing a counter/metric, that counter is observed non-zero in integration tests

### If Validation Fails

1. Identify which failures are caused by this plan's changes vs pre-existing
2. Fix all plan-caused failures before declaring the plan complete
3. Re-run the validation chain to confirm fixes
4. Pre-existing issues are logged but do NOT block plan completion (document them in the PR description)
