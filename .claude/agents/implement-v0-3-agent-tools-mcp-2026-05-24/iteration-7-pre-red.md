Skipping setPrototypeOf will break `instanceof` checks the classifier relies on across ESM/CJS boundaries.

- [MAJOR] — **`ContentTooLargeError` constructor SHAPE.** Plan deep dive says error text must reference `MAX_EMBEDDING_DIM`. BUT the constant lives at `src/core/constants.ts` (1536, pgvector HNSW cap). The text in plan T4.1 reads literally `"Content exceeds maximum embedding dimension ({MAX_EMBEDDING_DIM})."` — this is a TEMPLATE. The class MUST `import { MAX_EMBEDDING_DIM } from './constants.js'` and interpolate. Test `test_classify_content_too_large_returns_execution` should assert `text.includes('1536')` OR `text.includes(String(MAX_EMBEDDING_DIM))` — NOT a brittle exact string match. NOTE: arguably the cap is bytes-shaped (MAX_CONTENT_BYTES=50_000 at agent-tools surface), not dim-shaped. The plan deep dive is explicit about dim though — honor plan text verbatim; do NOT re-debate.

- [MAJOR] — **MissingScopeError discriminator: two callsite messages.** T3.1 ships TWO distinct MissingScopeError messages (verified `scope.ts`): (a) `withScope: ctx must be defined...` and (b) `getScope: no active scope...`. The classifier text in plan reads `'Scope not bound. Caller must invoke memoryFromCtx with ctx.session before tool call.'` — this is the SINGLE Tool Execution text emitted regardless of which inner message fired. Do NOT branch the execution text on inner message; classifier collapses both into one user-facing text. Test should assert `kind:'execution'` + `isError:true` + text matches plan literal — no inner-message coupling.

- [MAJOR] — **EC-13 stack/cause leak gate — assertion must be POSITIVE.** Plan: "do NOT leak stack trace OR `err.cause` chain". RED test must assert NEGATIVELY: construct `new Error('boom', {cause: new Error('inner-secret')})` with explicit `.stack` set, then assert classifier output's `data` field has NO `stack` key AND `data.message === 'boom'` AND `JSON.stringify(data)` does NOT contain `'inner-secret'`. Use `expect(JSON.stringify(result.payload)).not.toContain('inner-secret')` as the second-belt check — defense in depth against Error.cause auto-serialization in future node versions.

- [MAJOR] — **EC-5 PG_TRANSIENT_CODES branch ordering matters.** Plan declares the Set as `['ECONNREFUSED', 'ETIMEDOUT', 'ENOTFOUND', 'EPIPE', 'ECONNRESET']`. Branch logic: `err instanceof Error && typeof (err as {code?: unknown}).code === 'string' && PG_TRANSIENT_CODES.has(...)`. This MUST fire BEFORE the unknown-error fallback (else transient infra errors leak as -32603 = bug). It MUST fire AFTER the typed domain error branches (else a typed error with a coincidental `.code` field gets mis-classified). Recommended order in classifier: (1) ZodError → -32602; (2) MissingScopeError → execution; (3) MemoryStoreError → execution; (4) EmbedderError → execution; (5) ContentTooLargeError → execution; (6) PG_TRANSIENT_CODES check → execution; (7) UnknownToolError (if class exists by T4.1 — likely deferred to T5.1; otherwise classify-by-name string match per plan "Unknown tool name (from dispatch, Phase 5)"); (8) fallback → -32603. The unknown-tool branch is ambiguous: plan deep dive says it comes "from dispatch, Phase 5" — at T4.1, classifier MAY accept a sentinel like `UnknownToolError extends Error` declared in `error-classifier.ts` OR a string match. PREFER declaring `UnknownToolError` class inline in `error-classifier.ts` (single-file scope, not yet `src/core/`) so T5.1 dispatch can throw it; this keeps the classifier closed over its discriminators. Flag this design choice explicitly in test name and JSDoc.

- [MAJOR] — **ZodError detection — import path.** Use `import { ZodError } from 'zod'` then `err instanceof ZodError`. Do NOT match on `err.name === 'ZodError'` (brittle across zod minor versions).
