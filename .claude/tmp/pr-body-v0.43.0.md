### Fixed
- **IDOR cross-user destrutivo em `update_memory` + `forget` (M14 /review BLOCKER, segurança).** O `/review` (7 agentes, 4 confirmaram) achou que o forget do `update_memory` e o tool `forget` usavam `workspaceScopedMemory(...).forget(id)` (workspace-only); `LocalMemory.forget` só checa workspace, sem user — então um user X podia soft-deletar a memória do user Y no MESMO workspace passando o id dela. Corrigido roteando ambos pelo forget SUBJECT-SCOPED (`routeScopedMemory(...).forget` → `ScopedMemory.forget` → `deleteInScope` sobre o filtro (workspace,user)): um id fora do escopo lança `MemoryNotFound`, nunca deleta. O gate de isolamento do `update_memory` era vacuoso (o `emptyJsonLlm` retornava `[]` → remember 0 items → o forget nunca executava) — agora usa um LLM que extrai fato, provando que o forget É exercido e o alvo sobrevive. Gate cross-user do `get_memory` endurecido para fail-closed (row com `user_id` != acting → escondido, incl. NULL). Provado por `isolation.test.ts` 5/5 vs pgvector real.
- **`forgetEntity`/`delete_entities` sem observabilidade (M14 /review, Princípio 3).** A única superfície destrutiva do grafo não emitia evento. Adicionado `MEMORY_EVENTS.entity_forgotten` (contagens removidas) via tracer OTel opcional (no-op sem exporter, wired em `run-mcp-server`); é o audit trail que substitui um tombstone soft-delete (a tabela `entities` não tem `t_invalid` — o grafo é projeção re-extraível; [ADR-0022](.claude/knowledge-base/adrs/ADR-0022-m14-entity-forget-hard-delete-of-reextractable-projection.md) amenda ADR-M14-2). `PgMemoryEntityStore` refatorado (helpers `runInTx`/`scopeIds` em `pg-tx.ts`).
- **M14 T1.2 — captura user-authored "remember this" wired de fato.** O `/review` achou que a atribuição user-side (Bullet 2) não tinha caller de produção (só um teste que injetava `'user'` na mão). Implementado `detectUserRememberDirective` no `theo-prompt-recall` (EN/PT): um diretivo explícito do usuário dispara um remember `attributedTo:'user'` fire-and-forget.
- **IDOR cross-tenant E cross-user em `Memory.get` / MCP `get_memory` (M14 Phase 5, segurança).** `LocalMemory.get(memoryId)` retornava a linha por `WHERE id=$1` SEM checar o workspace (diferente do `forget`, que já validava — EC-5/#82): um `get_memory` no workspace A lia memória do workspace B, e um user X lia a de Y no mesmo workspace. O gate de isolamento da Phase 5 pegou o vazamento. Corrigido em duas camadas: (1) core — `LocalMemory.get` agora retorna `null` quando o `workspace_id` da linha ≠ workspace ligado (espelha `forget` EC-5); (2) handler `get_memory` — passa a exigir user ativo e esconde linha de outro user no mesmo workspace (gate cross-user, DoD bullet 6). Provado por `isolation.test.ts` (cross-tenant + cross-user, 5/5 vs pgvector real) + 3 unit tests.
- **Abas SESSION/AGENT da tela Entities sempre vazias (#119).** `filtersFor()` no handler REST montava a Filters de tier único (`{ session_id }`) SEM o `user_id` — mas entidades de session/agent tier carregam AMBAS as colunas (o write path deriva o escopo da memória-fonte, M8/ADR-0021), e o predicado da listagem é `COALESCE(user_id,'') = COALESCE($2,'')`. Resultado: uma sessão com 237 memórias e 712 entidades linkadas renderizava "No entities". Agora o acting user (Principal ou header da edge) é threadado nos filtros dos três tiers — o mesmo que o caminho de fallback do handler já fazia. RED-GREEN em `entities-readport.test.ts`.
