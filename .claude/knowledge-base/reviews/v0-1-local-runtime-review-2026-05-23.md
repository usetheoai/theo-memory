### F-dom-1: Vector literal serialization uses a string representation `[0.1, 0.2, ...]` and passes it to
parameterized queries as a string $N parameter, then casts via `::vector`. This works but the
pattern is brittle because the literal string must be syntactically valid pgvector input.
The comment claims "parameterized via $N::vector" but the implementation actually pre-constructs
the literal string and then parameterizes IT, not the raw numbers. Risk: if vectorLiteral()
produces a malformed string (e.g., NaN, Infinity, non-numeric values), the SQL will fail at
runtime with cryptic pgvector parse errors instead of being caught earlier.


- **Found by:** review-v0-1-local-runtime-domain-pgvector-schema
- **File:** `src/local/pgvector-store.ts` line 40-41
- **Plan reference:** Plan v1.3 § T3.3 + Blueprint D4
- **Domain anchor:** pgvector vector serialization: parameterized via ::vector
- **Evidence:**

  ```ts
  function vectorLiteral(vector: readonly number[]): string {
    return `[${vector.join(',')}]`;
  }
  
  // Later used as:
  params.push(vectorLiteral(vec));  // string like "[0.1,0.2,...]"
  // SQL: $N::vector
  ```
  Compare to Plan blueprint D4 reference (Mem0-ts): https://github.com/mem0ai/mem0/blob/main/js/src/oss/src/vector_stores/pgvector.ts
  Mem0-ts uses the same pattern, so this is acceptable precedent, but it means downstream
  consumers with malformed vectors will see pgvector parse errors rather than TypeScript type errors.

- **Recommended action:** ACCEPT (precedent from Mem0-ts proves this pattern). ADD: a guard in vectorLiteral()
to validate that all numbers are finite (not NaN, not Infinity). Recommended:
  function vectorLiteral(vector: readonly number[]): string {
    for (const n of vector) {
      if (!Number.isFinite(n)) throw new Error(`Invalid vector component: ${n}`);
    }
    return `[${vector.join(',')}]`;
  }
This converts a runtime pgvector error into an earlier, clearer JavaScript error.


### F-dom-3: Schema correctly pins embedding dimension to 1536 via `vector('embedding', { dimensions: MAX_EMBEDDING_DIM })`
and creates HNSW indexes with `vector_cosine_ops`. This is correct per ADR D1.7, which documented the
rationale: pgvector v0.5.1's HNSW index supports max 2000 dims, and 1536 covers OpenAI's embedders.

catch a future refactor that bumps MAX_EMBEDDING_DIM above the HNSW limit. If a future developer
changes `MAX_EMBEDDING_DIM = 2048` in constants.ts without reading ADR D1.7, the schema migration
will silently create an invalid HNSW index (creating beyond 2000 dims fails with `ERROR: column cannot have...`).

  but not machine-checkable. The constant MAX_EMBEDDING_DIM is imported from core/constants.ts (line 35),
  but there's no inline assertion.
  
  Compare to Plan ADR D1.7 § Consequences:

### F-dom-4: The search method at line 173-193 calls vectorLiteral(query) on the input query vector.

conversion to SQL. If a caller invokes `.search([0.1, 0.2])` (a 2-d vector), the SQL will
succeed but return wrong results because the cosine distance is computed between vectors
of mismatched dimension (pgvector silently zero-pads or fails). The factory probes the
embedder dimension (T7.1), but nothing validates that query vectors from retrieval pipeline
are correctly shaped.

  - compare to factory probeEmbedder() (src/local/index.ts:242-246), which validates

### F-dom-5: The history table declares a composite DESC index on (timestamp DESC, id DESC) at line 94.

by id DESC as a tiebreaker. Verified this works in Postgres 13+ (Docker image used is
Postgres 16 per ankane/pgvector:v0.5.1, so no risk). But worth documenting the rationale.


- **Found by:** review-v0-1-local-runtime-domain-pgvector-schema

  Generated SQL (migrations/0000_crazy_mimic.sql:39):

### F-dom-6: Line 155 appends vectorLiteral(vec) directly to the params array:
  params.push(id, text, hash, vectorLiteral(vec), JSON.stringify(cleanedPayload), userId, sessionId, agentId);

This is safe from SQL injection (the value is a string, then cast via ::vector), but it's
semantically different from truly parameterized queries. A future developer unfamiliar with
pgvector might try to parameterize the vector as $N directly (without conversion to string),
which would fail. The code is correct (mirrors Mem0-ts precedent), but the pattern is non-obvious.


- **Found by:** review-v0-1-local-runtime-domain-pgvector-schema
- **File:** `src/local/pgvector-store.ts` line 155
- **Plan reference:** Plan v1.3 § T3.3 + D1.1 (per-row fallback)
- **Domain anchor:** Vector serialization in batch insert: parameterization safety
- **Evidence:**

  src/local/pgvector-store.ts lines 153-155:
    values.push(`($${p++}, $${p++}, $${p++}, $${p++}::vector, $${p++}::jsonb, ...)`);
    params.push(..., vectorLiteral(vec), ...);
  
  The `$N::vector` cast is necessary because pgvector expects a string representation of a vector.
  This is working as designed, but could be clearer.

- **Recommended action:** ADD code comment clarifying the vector serialization pattern:

  // We parameterize the string and cast via ::vector for SQL injection safety.
  // Direct parameterization of numbers would require pgvector::binary support.
