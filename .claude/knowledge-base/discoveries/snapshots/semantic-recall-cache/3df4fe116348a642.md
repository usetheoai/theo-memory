## Verbatim key takeaway from source

> "Among these four, only Redis offers a true native query result/semantic cache layer as part of the same data platform as its vector search... For Pinecone, Weaviate, and Qdrant, caching typically requires bolting on an external cache (such as Redis itself, or application-level caching) since their official documentation does not describe a built-in query result cache layer."

## Implication for TheMemory v1.5

**STRONG validation of greenfield positioning at the SDK layer:**

1. **3 of 4 vendors don't ship this** — Pinecone/Weaviate/Qdrant consumers MUST bolt on external cache (Redis or app-level). TheMemory `RecallCacheStore` DIP fills this gap for pgvector consumers — same problem, different host vector DB.

2. **Redis's LangCache + RedisVL** is the ONE prior art that's "native". This validates the SURFACE direction (semantic cache co-located with vector store) AND informs the v1.5 alternative-backend: a `RedisRecallCacheStore` impl is a natural follow-up (v1.5.1) since Redis already supports the pattern natively.

3. **pgvector consumers are the BIGGEST untapped audience** — pgvector ecosystem (TheMemory's default; also used by Mem0 server, Letta, embedchain) has NO native semantic cache. Building `PgvectorRecallCacheStore` on top of TheMemory is THE missing primitive.

4. **70% LLM cost reduction claim** (Redis LangCache marketing) — sets the OBSERVABILITY direction: TheMemory v1.5 should EXPOSE hit-rate metric so consumers can compute their own cost reduction. Aligns with Item 19 acceptance criterion #2 (`recall_cache_hit_duration_ms` histogram).
