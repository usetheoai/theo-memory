## Negative finding — LlamaIndex does NOT ship semantic recall cache

LlamaIndex's `IngestionCache` is a **TRANSFORMATION-OUTPUT cache keyed by content HASH**, NOT a semantic similarity cache. Different problem class — caches "this node + this transformation → this output" not "this query semantically matches a cached query".

### What IngestionCache actually does (verbatim from docs)

> "Each node+transformation pair is cached, so that subsequent runs (if the cache is persisted) with the same node+transformation combination can use the cached result and save you time."

> "If a duplicate doc_id is detected and the hash has changed, the document will be re-processed and upserted; if the hash is unchanged, the node is skipped."

### Backends supported

- Redis (`RedisCache.from_host_and_port`)
- On-disk persistence (`pipeline.cache.persist("./llama_cache.json")`)
- Reloadable via `IngestionCache.from_persist_path(...)`

### LlamaIndex docs explicit recommendation (verbatim)

> "For semantic query result caching you would typically need to integrate RedisVL SemanticCache, GPTCache, or LangChain's RedisSemanticCache."

LlamaIndex itself **delegates semantic-recall caching to upstream libs** (GPTCache, RedisVL, LangChain). They do NOT compete in this space.

## Implication for TheMemory v1.5

LlamaIndex contributes ZERO semantic-recall threshold/invalidation evidence. The relevant LlamaIndex pattern is at a DIFFERENT layer (ingestion transformation cache):
- IF TheMemory v1.5 ever needs to cache LLM-extraction outputs (the 8-phase write pipeline's Phase 2 LLM extraction), LlamaIndex IngestionCache pattern (hash-keyed content cache) is the precedent
- For QUERY-result caching (Item 19 scope), LlamaIndex points to LangChain / GPTCache → consistent with Q6 (GPTCache) + Q7 LangChain side (covered separately)
