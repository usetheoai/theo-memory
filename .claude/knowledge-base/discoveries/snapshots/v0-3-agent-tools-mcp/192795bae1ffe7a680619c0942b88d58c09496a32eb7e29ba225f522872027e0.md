# Base Protocol (MCP 2025-11-25)

The Model Context Protocol consists of several key components:
- **Base Protocol**: Core JSON-RPC message types
- **Lifecycle Management**: Connection initialization, capability negotiation, session control
- **Authorization**: Auth framework for HTTP-based transports
- **Server Features**: Resources, prompts, tools
- **Client Features**: Sampling and root directory lists
- **Utilities**: Logging and argument completion

All implementations MUST support the base protocol and lifecycle management components.

## Messages

All messages MUST follow JSON-RPC 2.0.

### Requests
```typescript
{
  jsonrpc: "2.0";
  id: string | number;
  method: string;
  params?: { [key: string]: unknown };
}
```
- Requests MUST include a string or integer ID.
- Unlike base JSON-RPC, the ID MUST NOT be `null`.
- The request ID MUST NOT have been previously used by the requestor within the same session.

### Result Responses
```typescript
{
  jsonrpc: "2.0";
  id: string | number;
  result: { [key: string]: unknown };
}
```
- Result responses MUST include the same ID as the request.
- Result responses MUST include a `result` field.

### Error Responses
```typescript
{
  jsonrpc: "2.0";
  id?: string | number;
  error: {
    code: number;
    message: string;
    data?: unknown;
  };
}
```
- Error responses MUST include the same ID as the request (except when ID could not be read due to malformed request).
- Error responses MUST include an `error` field with a `code` and `message`.
- Error codes MUST be integers.

### Notifications
```typescript
{
  jsonrpc: "2.0";
  method: string;
  params?: { [key: string]: unknown };
}
```
- Notifications MUST NOT include an ID.
- The receiver MUST NOT send a response.

## Auth

MCP provides an Authorization framework for use with HTTP. HTTP-based transports SHOULD conform. STDIO transports SHOULD NOT — instead retrieve credentials from the environment.

## Schema

Full spec is a TypeScript schema at github.com/modelcontextprotocol/specification/blob/main/schema/2025-11-25/schema.ts. A JSON Schema is auto-generated.

## JSON Schema Usage

### Schema Dialect

1. **Default dialect**: When a schema does not include `$schema`, defaults to JSON Schema 2020-12.
2. **Explicit dialect**: Schemas MAY include `$schema` to specify a different dialect.
3. **Supported dialects**: Implementations MUST support at least 2020-12 and SHOULD document additional dialects.
4. **Recommendation**: Use JSON Schema 2020-12.

### Implementation Requirements

- Clients and servers MUST support JSON Schema 2020-12 for schemas without explicit `$schema`.
- Clients and servers MUST validate schemas according to declared or default dialect. They MUST handle unsupported dialects gracefully by returning an appropriate error.

## General fields

### `_meta`
Reserved by MCP for additional metadata. Key names have prefix (optional, reverse DNS notation) + name. Prefixes with second label `modelcontextprotocol` or `mcp` are reserved.

### `icons`
Visual identifiers. Each Icon has `src` (HTTPS or data: URI required — javascript:/file:/ftp:/ws: REJECTED), optional `mimeType`, `sizes`, `theme`. Required MIME types: image/png, image/jpeg. SHOULD support image/svg+xml, image/webp.
