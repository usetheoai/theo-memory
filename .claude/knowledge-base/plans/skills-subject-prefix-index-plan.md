# Plan: skills-subject-prefix-index (M2 — SEC-1)

> Performance / multi-tenant-scalability hardening of the cross-repo skills listing shipped in `skills-cross-repo-flat-list` (themory v0.21.0). The `/review` domain+security agent (SEC-1, MEDIUM) found that `PgvectorStore.listSkillsBySubject` runs `agent_id LIKE '{subject}:%'`, which CANNOT use the default `text_ops` btree opclass under a non-`C` collation (e.g. `en_US.utf8`) → a **Seq Scan + Sort over the `workspace_id='default'` partition**, which — under the gateway master-key tenancy model — holds EVERY customer's skills. This is a PERF/DOS concern, NOT a tenant-isolation bug (isolation is correct and already tested). This plan adds the index that makes the prefix range-scannable. No public-API change, no query change — the planner picks the index once it exists.

## Goal

> "Add a `(workspace_id, agent_id text_pattern_ops)` partial btree index (`WHERE kind='skill' AND t_invalid IS NULL`) so `listSkillsBySubject`'s `agent_id LIKE '{subject}:%'` prefix is index-range-scannable, measured by `tests/integration/skills-subject-prefix-index.test.ts` which (a) structurally asserts the shipped index uses the `text_pattern_ops` opclass on `agent_id`, and (b) behaviorally `EXPLAIN`s the cross-repo prefix query under `enable_seqscan=off` and asserts an `Index Cond` scan on `idx_memories_skill_subject_prefix` — NOT a `Seq Scan on memories` — against real `ankane/pgvector:v0.5.1`, with the existing `skills-cross-repo-flat-list` GOAL still green (results byte-unchanged)."

## Context

The `skills-cross-repo-flat-list` cycle (v0.21.0) shipped a tenant-safe cross-repo skills listing whose load-bearing selectivity is the `agent_id` PREFIX `'{subject}:%'` (the gateway bakes the tenant into the `agent_id` prefix; `workspace_id` is `'default'` for every customer under the master key). Its `/review` flagged SEC-1 (MEDIUM): a btree index with the **default `text_ops` opclass** does NOT support `LIKE 'prefix%'` as a range condition under a collation other than `C` — Postgres falls back to a Seq Scan of the whole `memories` table (filtered post-scan). Because the only selective predicate is the prefix, and the `workspace_id='default'` group contains all tenants, this scan grows linearly with total skill volume across all customers; deep `offset` compounds it. SEC-1 was accepted as a fast-follow at release (dev scale is tiny) and recorded as Drawback #4 of the cross-repo plan + roadmap M2. This plan closes it.

The canonical fix is the `text_pattern_ops` operator class: a btree opclass that compares using raw byte ordering (collation-independent), which makes `LIKE 'prefix%'` an indexable left-anchored range (`col ~>=~ 'prefix' AND col ~<~ 'prefiy'`). It is the textbook Postgres answer for prefix-LIKE acceleration and works under ANY collation (so the fix is correct whether CI's pgvector image is `en_US.utf8` or `C`).

### Domain glossary

- **`text_pattern_ops`** — a builtin Postgres btree operator class that orders text by raw byte value (ignoring collation), making `LIKE 'prefix%'` / `~` anchored patterns index-range-scannable. Supports `LIKE`/`~` prefix; does NOT support `ILIKE` (case-insensitive) — the residual `description ILIKE` filter therefore stays a post-scan filter (acceptable; the `agent_id` prefix is the selective clause).
- **partial index** — `CREATE INDEX ... WHERE kind='skill' AND t_invalid IS NULL`; only skill, live rows are indexed → small index. The planner uses it only when the query's WHERE IMPLIES the partial predicate; the cross-repo query has both `kind='skill'` and `t_invalid IS NULL` literally, so the implication holds.
- **`Index Cond`** — the EXPLAIN line proving a predicate was pushed into the index as a scan bound (vs a post-scan `Filter`). Presence of `Index Cond` on the prefix is the proof the opclass made the LIKE range-scannable.

## ADRs

### D1 — `text_pattern_ops` opclass over `COLLATE "C"` index, ICU collation, or trigram (`pg_trgm`)

- **Decision:** create a btree index `(workspace_id, agent_id text_pattern_ops)` partial on `WHERE kind='skill' AND t_invalid IS NULL`.
- **Rationale:** `text_pattern_ops` is the minimal, builtin, dependency-free way to make `LIKE 'prefix%'` index-range-scannable independent of the database collation (KISS + Rule 9 — use the platform primitive, don't reinvent). It exactly serves the shipped query (`agent_id LIKE '{subject}:%'`).
- **Alternatives rejected:**
  - **`COLLATE "C"` on a re-typed column** — would require altering the `agent_id` column collation (touches a column used by other queries/indexes; migration risk; behavior change). Rejected — heavier and wider blast radius than an additive index.
  - **ICU collation database** — infra-level change to the whole DB; out of proportion for one prefix query. Rejected (YAGNI).
  - **`pg_trgm` GIN trigram index** — supports arbitrary substring/`ILIKE`, but is larger, slower to build, and overkill for a left-anchored prefix; adds an extension dependency. Rejected (KISS + Rule 9 — don't pull a heavier extension for a prefix the builtin opclass already serves).

### D2 — Composite `(workspace_id, agent_id)` leading with `workspace_id`, partial on skill+live

- **Decision:** lead the index with `workspace_id` (equality), then `agent_id text_pattern_ops` (range), partial `WHERE kind='skill' AND t_invalid IS NULL`.
- **Rationale:** matches the query's predicate shape exactly — equality on the leading column + anchored range on the second column is the canonical btree composite. The partial predicate matches the query's constant predicates (`kind='skill'`, `t_invalid IS NULL`), keeping the index small and ensuring the planner can use it. Mirrors the roadmap M2 specification verbatim.
- **Alternatives rejected:**
  - **Single-column `(agent_id text_pattern_ops)`** — would still serve the prefix, but the composite keeps the index aligned with the full equality+range predicate and consistent with the existing `idx_memories_user_attributed_to` composite-partial precedent. Kept the composite for predicate alignment.
  - **Non-partial index** — would index every memory row (extracted/derived/skill, live + soft-deleted), bloating the index for a query that only ever touches live skills. Rejected.

### D3 — Migration via `drizzle-kit generate` (schema.ts as source of truth), not a hand-written SQL-only migration

- **Decision:** declare the index in `schema.ts`, then run `npm run db:generate` to emit `0021_*.sql` + `0021_snapshot.json` + the journal append atomically.
- **Rationale:** the repo maintains schema.ts ↔ snapshot parity (enforced by `schema-snapshot-parity.test.ts`; the `db:push` dev workflow diffs against schema.ts). A SQL-only migration without a schema.ts declaration would make `drizzle-kit push` compute a destructive DROP-INDEX diff (drift). Using the tooling is the no-rework path and keeps all four artifacts consistent.
- **Alternatives rejected:**
  - **Hand-written `.sql` + hand-edited snapshot** (the 0009 precedent) — error-prone snapshot JSON authoring; `db:generate` produces it deterministically. Fallback only if `generate` emits unexpected drift (verified by inspecting the generated SQL — it MUST contain only the one `CREATE INDEX`).

> **EC-4 (production correctness note):** `listSkillsBySubject` calls `this.pool.query(sql, params)` — node-postgres sends an UNNAMED extended-protocol statement, which Postgres plans FRESH each execution with the actual `'{subject}:%'` value bound (a CUSTOM plan). The generic-plan-ignores-LIKE pitfall only affects NAMED prepared statements promoted after ≥5 executions (not used here). This is WHY the index closes SEC-1 in production, not only in the literal-pattern test.
