# Milestone M7 — Claude Code ⇄ theo-memory via the Theo MCP Gateway (dev)

## Objective (from ROADMAP.md)

Every Claude Code instance uses theo-memory in the dev environment through the Theo MCP Gateway
behind Traefik, with the client holding exactly one secret — a scoped `theo_live_*` — and the
gateway performing MCP-aware auth plus downstream credential injection (Model B).

## Progress — Phase 1 (evidence-backed)

### T1.1 — Re-point the ForwardAuth validator at the canonical store ✅ DONE

Root cause: split-brain. The dashboard minted into the k3d Postgres (12 keys, 4 users, 4 tenants)
while the compose validator read `theo-workspace-pg-cloud-1` (0/0/0), so every `theo_live_*` was
indistinguishable from a forgery (`scope.go` collapses unknown/revoked/expired into one error).

Network path proven before changing anything: `k3d-theo-mgmt-server-0:30432` on the `k3d-theo`
docker network reaches the canonical store (NodePort 30432; the pre-existing `:15432` port-forward
is bound to `127.0.0.1` and unreachable from containers).

Applied to `compose.override.yml` (untracked, so safe for the credential) with a
`compose.override.yml.bak-pre-m7` backup and `docker compose config` validation before recreate.

**Acceptance — met:**

| Case | Before | After |
|---|---|---|
| Valid `theo_live_*` on `/v1/memory/skills` | 401 `AUTH_REQUIRED` | **400 `INVALID_REPO_ID`** — passed auth, reached handler validation |
| Invalid key | 401 | 401 (still denied) |
| No credential | 401 | 401 (still denied) |

### T1.2 — Expose `/mcp/*` at the public edge ✅ DONE

`/mcp/*` had no `handle` block in the Caddyfile, so it fell to the catch-all `file_server` and
returned the SPA (`200 text/html` on GET, `405 allow: GET, HEAD` on POST — the static-file-server
signature). The gateway itself was already deployed and fail-closed.

Added a `handle /mcp/*` block routing to the data-plane edge (`localhost:8092`), mirroring
`/v1/memory/*`, in **both** the running config (`theo/.local/Caddyfile`) and the source
(`theo/infra/local/Caddyfile`); backups `*.bak-pre-m7`; `caddy validate` passed before reload.

Note: `caddy validate` fails on the *unmodified* config too unless `CLOUDFLARE_API_TOKEN` is
supplied — a validation invocation detail, not a config defect.

**Acceptance — met:**

| Case | Before | After |
|---|---|---|
| `POST /mcp/memory`, no credential | `405`, `server: Caddy`, `text/html` (SPA) | **`401 {"error":"credential denied"}`, `application/json`** |

## Remaining blocker — Model B was never provisioned on dev

With auth and routing fixed, the chain now runs end-to-end **up to the final mint**:

```
mcp-resolve: per-tenant mint failed  tenant=tn-f50e039ca488a1bc  capability=memory
  error: "themory: not found"
```

The credential resolves to a tenant and the capability `memory` is accepted (this also answers the
blueprint's Unresolved Question 3 — the capability segment is `memory`). The failure is the
per-tenant mint: theo-memory returns 404 because its **admin API is not mounted** —
`run-server.ts:207-209` mounts it only when `THEMORY_ADMIN_BOOTSTRAP_TOKEN` is set, and the
deployed `themory_app` has no such variable.

Two further defects found and fixed along the way:

- `THEMORY_BASE_URL` pointed at `host.docker.internal:18081` — the **local-env** convention. On dev
  `themory_app` publishes `:8080`, and it sits on a different compose network (`theo-memory_default`),
  so the name never resolved. Fixed to `:8080` plus the missing
  `extra_hosts: host.docker.internal:host-gateway` mapping the author's intent required.

## Security ordering — why the last step was NOT taken

Enabling a key-minting admin API on `themory_app` is the remaining action, and it is deliberately
**not** done yet: that service is published on `0.0.0.0:8080` and accepts unauthenticated reads and
writes from the public internet (**issue #101**). Mounting key minting on an open service would
create a worse vulnerability than the one being fixed.

Correct order: close #101 first (`THEMEMORY_REQUIRE_CREDENTIAL=true`, per the theo-cloud ROADMAP's
own prod-gate note, and/or bind `:8080` to loopback), then enable the admin API, then provision
`THEMORY_PLATFORM_ADMIN_KEY` via `dev/provision-model-b.sh`.

## Additional finding (reported, out of M7 scope)

A Cloudflare API token is passed in the Caddy process arguments and is readable by **any local
user** via `ps` / `/proc/<pid>/cmdline`. This session read it that way to run `caddy validate`,
which demonstrates the exposure. It must be rotated and moved to a restricted environment file.

Order was security-driven: mounting a key-minting admin API on a service that accepted

| Case (public `:8080`, no credential) | Before | After |
|---|---|---|
| `POST /v1/remember` | **201 CREATED** | **401 `UNAUTHORIZED: Bearer token required`** |
| `POST /v1/recall` | 200 | **401** |
| `POST /v1/admin/keys` | 404 (API not mounted) | **401** (mounted, gated) |

Then minted the platform-admin credential (`apk-76daf41b6df76d14`, scopes
`memory:platform-admin` + `memory:admin` — lifecycle only, no data verb, per invariant 4)
and set `THEMORY_PLATFORM_ADMIN_KEY` on `theo-workspace-theo-cloud-1`.

Mint result: the gateway advanced from `503 auth_backend_unavailable` → `502 upstream_error`.

### T1.4 — Run the MCP upstream ✅ DONE

`502 upstream_error` had a blunt cause: **dev never ran an MCP server at all.** The gateway
expected `https://host.docker.internal:18091`; only `themory server` (REST, :8080) existed.
The canonical runner (`theo-workspace/dev/mcp-up.sh`) assumes a host process from a developer
checkout — there is no such process on the dev droplet.

Added a `themory_mcp` service to `docker-compose.deploy.yml` (same image, `mcp` verb).
**Deliberately not published to the host:** `host.docker.internal` maps to the bridge gateway
IP, so a loopback publish is unreachable from the gateway container and a reachable publish
means `0.0.0.0` on a shared box — the issue-#101 exposure class. It joins the gateway network
and is addressed by service name; the port never leaves the docker bridge. TLS uses the dev
keypair the gateway already trusts (SAN extended for the service name, backup kept) and
`--auth api-keys` keeps the upstream fail-closed on its own.

**Acceptance — met.** Full MCP `initialize` through the public edge:

```
POST https://app-dev.usetheo.dev/mcp/memory   (Authorization: Bearer theo_live_*)
HTTP/2 200 · content-type: text/event-stream · mcp-session-id: 5d7ec287-…
{"result":{"protocolVersion":"2025-06-18","serverInfo":{"name":"themory","version":"0.3.0"}}}
```

### T1.5 — Product defect: only ONE MCP client could ever connect ✅ FIXED

Registering Claude Code surfaced a real defect, not a misconfiguration. The second handshake
returned:

```
HTTP 400 {"error":{"code":-32600,"message":"Invalid Request: Server already initialized"}}
```

`connectStreamableHttp` shared ONE `StreamableHTTPServerTransport` across all requests. An SDK
transport binds its session at the first `initialize`, so every client after the first was
rejected — which makes the milestone objective ("every Claude Code instance") impossible. The
source comment anticipated only the multi-*instance* case; the single-instance case was already
broken.

Fixed with the SDK-canonical shape: `McpSessionRegistry` keyed by `Mcp-Session-Id`, one
transport + one `McpServer` per session, eviction on close, 404 (not a silent new session) for
an unknown id. `connectStreamableHttp` now takes a server factory, since an `McpServer` binds
one transport at a time.

TDD: `streamable-http-multisession.test.ts` written RED (2/2 failing), then GREEN. Transports
suite 39/39; MCP package 140/141 — the one failure is a pre-existing slow test that times out
at 5s and passes at 30s, equally slow on `origin/develop` (confirmed by stashing).

Commits: `ee6fb05` (MCP upstream service), `5c44f8d` (per-session fix).

## Phase 3 — /review found real defects, including one I introduced

Three independent reviewers returned **NEEDS_FIXES**. The findings were correct.

### Tenant isolation was broken by this milestone's own deploy (BLOCKER)

`withScope` REPLACES the AsyncLocalStorage context; it does not merge. The tools/call
handler wrapped dispatch in `withScope({ session: { userId } })`, discarding the
`workspaceId` resolved from the Principal. That branch runs whenever a user id is
resolvable — and the MCP service I deployed sets `THEOMEM_MCP_DEFAULT_USER_ID`, so it
ALWAYS ran. Every tenant's tool calls executed against unbound memory under one shared
user id.

Fixed by merging the outer scope. Regression test verified RED on the old code
(`expected undefined to be 'wk-tenant-a'`) and GREEN after.

## Honest gap — cross-tenant isolation is NOT proven at the edge

The gateway validates customer credentials against theo-cloud's store (k3d Postgres);
keys minted through theo-memory's admin API live in a different store and are denied at
the edge. Both `theo_live_*` keys available here resolve to the SAME tenant
(`tn-f50e039ca488a1bc`), so the edge-level cross-tenant case cannot be satisfied from
this repo — it needs a second dashboard account. The data-plane proof above covers the
half this milestone changed; the edge half remains unverified.
